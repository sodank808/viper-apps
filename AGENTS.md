# AGENTS.md

Guidance for AI coding agents (Claude Code, Codex, Cursor, etc.) working in this repository.

## What this is

Apps for Viper, a mini operating system for ESP32-S3 handhelds (ESP-IDF 5.5, C++20, LVGL 9.3). Viper loads them at run time as ELF files; this repo holds the ones whose source is public. The firmware lives in a separate repo, which mounts this one at `apps_public/` as a git submodule.

- Each top-level folder with a `CMakeLists.txt` is one app, an ESP-IDF project built with `idf.py elf` (`make APP=<app>`; `make` builds them all into `out/`).
- `sdk/` is generated by the firmware repo's `make sdk` (`scripts/export_sdk.py`). Don't edit it here: a change to the API or build rules is made in the firmware repo and comes back as an SDK update. The firmware's tests fail when `sdk/` doesn't match what it would generate.
- Readers start with `README.md`; the app API is documented in `sdk/include/viper_app.h`.

## Apps

- A project's `CMakeLists.txt` sets `COMPONENTS main`, includes ESP-IDF's `project.cmake`, calls `project(<app> C CXX)`, optionally `set(VIPER_LIBS ...)`, then `include(../sdk/viper_sdk.cmake)` and `project_elf(<app>)`. Sources go in `main/`. `sdk/README.md` has the template.
- An app's folder name is its bundle id, `app.viper.<folder>`; it also has an `info.json` (name, type, `url`, extensions) and an `icon.png`. Anything in its `assets/` folder is installed beside `app.elf`, and the app finds it with `viper_app_path()`.
- An app reaches the OS only through `viper_app.h` (and `viper_link.h` for link play) and LVGL. What it may call from the firmware is in `sdk/exports/*.txt`; `sdk/tools/check_app_elf.py` runs after every link and fails the build if the app calls anything else. If an app needs a firmware function that isn't exported, it has to be added in the firmware repo first.
- Apps run from PSRAM, are loaded and unloaded many times per session, and must free everything when destroyed. Internal RAM is tight; avoid allocating in the per-frame loop.
- C++ apps: no exceptions or RTTI.
- Apps with large assets go on the SD card: list them in `SDCARD_APPS` in the `Makefile`.
- Apps that also run in the firmware repo's host simulator are compiled into it from source, so app code must build for a 64-bit host as well as the ESP32-S3.

## Tests

The host simulator is part of the firmware repo, so app tests build and run only there (with this repo at `apps_public/`). An app's tests go in `<app>/tests/`: `test_<app>_boot.cpp` for the app on the booted OS (picked up by name), and unit tests listed in `tests.cmake`. Here, building every app (`make`) is the check; CI does the same.

## Licenses

The repo is MIT. Third-party code in an app keeps its own license file in that app's folder (e.g. `doom/main/prboom/COPYING`), and `README.md`'s table lists it. Don't add game data unless its license allows redistribution, and never commercial ROMs.

## Code style

- clang-format (`.clang-format`, LLVM-based, 4-space indent) for first-party code. Leave vendored third-party code in its upstream style and mark local changes with a comment.
- Members use a trailing underscore (`logger_`, `container_`).

## Docs and git

- Each app has a `README.md`: what it is, how to play, its third-party code and license, and what's untested on hardware.
- Changes go through pull requests into `main`. Don't commit `build/`, `out/`, `sdkconfig` or game data.
