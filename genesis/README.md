# Genesis

Status: runs in the host simulator and on a Viper Proto1 (Sonic 2 emulates at 60 fps, showing about 28 frames a second), 2026-11-24.

A Sega Genesis / Mega Drive emulator as an ELF app (`app.viper.genesis`, `genesis://`, opens `.md`, `.gen` and `.smd`). The core is [gwenesis](https://github.com/bzhxx/gwenesis) as esp-box-emu runs it on the ESP32-S3 ([esp-cpp/gwenesis](https://github.com/esp-cpp/gwenesis), branch `esp32` at `2af750e`), vendored in `main/gwenesis/`. It installs to the SD card (`SDCARD_APPS` in this repo's `Makefile`): at 640 KB it doesn't fit in what's left of the firmware's fatfs image. It needs firmware with app API level 6 (`viper_thread_create()`, `viper_frame_set_swap()`).

## Controls

| Viper | Genesis |
| --- | --- |
| D-pad | D-pad |
| Y, B, A | A, B, C (their order on the Genesis pad, left to right) |
| X | C |
| Start | Start |
| Select | Pause menu: resume, save state, load state, the 68000's clock, reset, quit |

Holding Select still closes the app, as in every app. B is the game's, so it doesn't go home while a game runs (it does from an error screen).

## What's here

- `main/gwenesis/`: the core, upstream's `src/` flattened into one folder (the simulator puts only `main/` on the include path) plus `genesis_dualcore.h` from its `port/`. Every change is marked `Viper:`. The debugger (`Debug.c`, `ConDebug.c`) and the precomputed 68000 tables are left out.
- `main/gwenesis/gwenesis_port.h`: the build settings, included first by every core source, since the simulator compiles the app's sources without `main/CMakeLists.txt`'s flags.
- `main/genesis_core.{h,cpp}`: the machine: where its memory lives, the frame loop (esp-box-emu's single-core path in `port/genesis.cpp`), the pad, the sound mixed to mono, the palette, save states. No `viper_*` calls, so the unit tests drive it directly.
- `main/main.cpp`: the app: loading the ROM, pacing and frame skip, the indexed frame, the audio ring the tap resamples from, the pause menu.
- `tests/`: `test_genesis.cpp` (the machine on `smoke.md`, `[genesis]` in `viper_sim_app_tests`) and `test_genesis_boot.cpp` (the app on the booted OS: the ROM picker, the picture, the pad, the menu, save states). `smoke.md` is generated by `sim/tests/roms/make_test_roms.py` in the firmware repo, which keeps the test ROMs; there are no commercial ROMs in either repo.

## Memory

PSRAM is what limits this on a device (about 1 MB free at the home screen on one with 8 MB, by the Doom app's measurements), so:

- **The ROM** goes in the firmware's 2 MB emulator ROM buffer, borrowed through `viper_memory_scratch()`; the built-in emulators don't run while an ELF app does. A ROM bigger than 2 MB (padded up to a power of two: 3 MB and 4 MB games need 4 MB) is tried on the heap, which on most devices won't have room. Games up to 4 MB without a mapper run; Super Street Fighter II's mapper isn't emulated.
- **The 68000's opcode table** is a 16-bit index per opcode into Musashi's handler list (128 KB), built when the machine starts, instead of upstream's precomputed handler pointers and cycle counts (320 KB, and 64K relocations for the loader). It rebuilds upstream's full tables exactly. (Upstream's ESP build used the smaller precomputed table, which stops at opcode 0xEFBF, so line-F opcodes jumped past its end.)
- **Internal RAM**: the hot, small state is in the loader's shared 64 KB pool (`.shared_dram`, 55 KB): the YM2612's tables and state, the CPU, the Z80's RAM, the VDP's tables and line buffers, the sound buffers. The 68000's work RAM and VRAM (64 KB each) don't fit beside them and are in PSRAM; esp-box-emu found work RAM the most worth having internal, so which buffers go where is the first thing to measure on hardware.
- **The VDP's copy of its state** for drawing (VRAM, the sprite table, the registers and VSRAM of each line: 105 KB) comes from the heap.
- **The rest of the machine's memory** (work RAM, VRAM, the opcode index and the YM2612's LFO table, 288 KB) goes in the same buffer after the ROM when there's room, which there is for ROMs up to 1 MB; bigger ROMs take it from the heap, largest block first. On a Proto1 the heap had 545 KB free with the app loaded, but its largest block was 248 KB, so the four allocations didn't fit there.
- The app's code and data take about 450 KB of PSRAM when it's loaded. (The loader used to keep the 630 KB file in memory too while the app ran; it now frees it once the app is loaded, and a file it can't read into memory is an error instead of an abort.)

## Picture

The VDP draws palette indices straight into the frame that `viper_frame_set_indexed()` has the display stretch to the screen, H40 at 320 wide and H32 at 256 (stretched to the full width, as on a TV), 224 lines (240 in PAL's V30). It needs a screen at least 320 x 224.

Only 64 colors are live at a time, and gwenesis keeps four copies of them in its 256-entry palette (the top two bits of each pixel are priority bits). The app uses the four blocks for up to four versions of the palette within a frame: when the game changes a color partway down (the water line in Sonic), the lines from there on point at a new block. A fifth change in one frame reuses the fourth block. Shadow and highlight aren't drawn (upstream doesn't either).

## Sound

The YM2612 and the PSG at half the YM2612's rate (26.6 kHz NTSC), as esp-box-emu runs them, mixed to mono and handed a frame at a time to the firmware's audio stream (`viper_audio_stream_*()`), which plays it at the output's rate. It paces the sound as the built-in emulators' is (`components/emu_host`, "Pacing sound"): when frames come late it time-stretches the sound, keeping its pitch, instead of letting the speaker run dry. The timing line in the log says how much (`sound stretched N%`).

## Performance

The Z80 and the sound chips run on a second thread (`genesis::set_threaded()`, esp-box-emu's dual-core split): the app's thread runs the 68000 and the VDP, the sound thread follows a scanline behind at most, the 68000's writes to the sound chips go through a queue, and a Z80 bus request waits for the sound thread to stop between lines. The unit tests run both ways; one thread is deterministic, which the save state test needs.

The sound thread is started with `viper_thread_create()` as `genesis_snd`, on core 1 at the high level (priority 20 there: the display's video task, at 19, waits for it; at 18 the video task's sends made each frame wait longer for the sound). The app's thread is the firmware's main task, on core 0.

On a device the picture is drawn in the app thread's spare time (`genesis::set_spare_time_drawing()`): as the 68000 runs a frame, each line's VDP registers and VSRAM are recorded, and the lines are drawn afterwards, while the thread waits for the sound thread at the end of a frame and between frames, from a copy of VRAM and the sprite table taken as the frame started (only the 256-byte blocks of VRAM that changed are copied). A new frame is recorded only once the last one has been drawn and presented, so drawing takes whatever time is left and never slows the game; the frames between are skipped. That replaced a frame skip that had to guess, from running averages, how many frames to skip. The simulator's app and most tests draw each line as it's run, so a frame is on the screen when the next starts; one unit test checks that both ways draw the same picture.

Indexed frames are presented with `viper_frame_set_swap(1)`: every drawn frame writes every pixel, so the display sends one half of the 8-bit buffer while the next frame goes in the other, instead of a 70 KB copy a frame.

### Measuring

Numbers come from Sonic 2 played from a save state at the start of Emerald Hill Act 1 (the app's own, saved from its menu): load it, hold right and jump every 2 s, and average six of the app's 5-second timing lines after the first. The attract demo is no good for this: it cycles through stages, including the heavier two-player race. Profiles come from `viperctl profile` on the main task; an ELF app's PCs are mapped back by finding its load address (the one offset at which every sampled PC starts an instruction) and relinking `build/esp-idf/main/libmain.a` without stripping, which gives the same layout with symbols and lines. The profiler samples from core 0, so the sound thread's code is profiled in a build with `set_threaded(false)`.

On a Proto1 (2026-11-24), over 30 s of that run:

| | Frames drawn | A drawn frame | A skipped one | Emulated |
| --- | --- | --- | --- | --- |
| Before (sound thread on inherited settings) | 470-575 of 1800 | 23.5-25.5 ms | 11.9-12.4 ms | 59.2-59.8 fps |
| Jump tables, cheaper stretch search, swapped frame buffers | 680-900 of 1800 | 20.3-22.2 ms | 10.5-11.3 ms | 59.3-60.0 fps |
| Drawing in spare time | 780-865 of 1800 | 11.3-11.9 ms | 10.8-11.0 ms | 60.0 fps |

With frame skip, the spread between runs was it settling at 1 (every other frame drawn) or 2, and drawn frames ran over the frame's time, so the game dipped below 60 fps. Drawing in spare time, a drawn frame's own time is about a skipped one's (the drawing happens outside it, in about 30 ms of spare time spread over the next frames), the game holds 60 fps, and about 28 frames a second are shown. The display isn't the limit: it shows 42 a second on the title screen. Where the time went before this change, on the app's thread, on the app's thread: the 68000 about 45% (its instruction fetch alone 12%: every word comes from the ROM in PSRAM), the VDP about 22%, waiting for the sound thread at the end of a frame about 8%, copying each drawn line from internal RAM to the frame about 4%; on the sound thread the Z80 about 55% and the YM2612 about 40%.

What helped and what didn't:

- **Jump tables** (`-fjump-tables` in `main/CMakeLists.txt`): ESP-IDF turns them off for every component, which made the Z80's opcode switch a chain of compares. The sound thread's CPU went from ~58% to ~51%, halving the app thread's wait for it.
- **Swapped frame buffers** (`viper_frame_set_swap()`): about 3 ms off each drawn frame, and the biggest gain in frames shown.
- **The audio stretcher's alignment search** (`components/emu_host`): coarse to fine, a third of the work. It runs on the app's thread whenever the game dips below 60 fps.
- **A two-level opcode table** (377 distinct 32-opcode blocks, 24 KB, with the 4 KB first level in internal RAM, instead of 128 KB in PSRAM): no measurable change, but 100 KB less PSRAM touched, so it stays.
- **The 68000 core at -O2** instead of -Ofast (37 KB less code, for the instruction cache both cores share): no change; left at -Ofast.
- **The sound thread at priority 18**, below the display's video task: undrawn frames took ~14 ms instead of ~11; it's at 20.
- **Drawing in spare time**: the game at a steady 60 fps (it dipped to 59-59.6), and about as many frames shown as frame skip's best runs (780-865 of 1800, against 660-900). The main task is busy ~87% of core 0 instead of ~92%.
- **Drawing on a thread of its own** (the same recorded lines, drawn by a low-priority thread on core 1 or either core): fewer frames shown (600-660 of 1800). Core 1 is nearly full with the sound thread (~50%) and the display's video task (~20%), so a frame took ~36 ms to draw there. Sharing the lines between that thread and the app's needed an atomic exchange a line, and ELF apps have no hardware atomics (`-mdisable-hardware-atomics`: each one is a call into the firmware that takes a spinlock with interrupts off), which starved both and tripped the task watchdog.
- **The data cache's lines at 64 bytes** instead of 32 (a firmware setting, `CONFIG_ESP32S3_DATA_CACHE_LINE_64B`): no change beyond the spread between runs; left at 32.
- **Work RAM or VRAM in internal RAM**: not possible as things are. With the app running, internal RAM has ~30 KB free, its largest block 22 KB, after the loader's 64 KB shared pool (which holds the YM2612, the CPU, the Z80's RAM and the VDP's tables).

## Limits

- No battery-backed SRAM (gwenesis has none): games that save to the cartridge (Phantasy Star, Sonic 3) lose it. Save states work.
- No 6-button pad, no second player, no mapper (SSF2), no Mega CD or 32X.
- On a device, a write to VRAM or the sprite table while the picture is being shown (rare: games make them in vertical blanking) shows from the next frame drawn on, not from the line it was made on (genesis_core.cpp, "Drawing in spare time"). Register, VSRAM and palette changes partway down still take effect on their line.
- Interlace mode 2 (448 lines: Sonic 2's two-player mode and its attract demo) is drawn as its even field, every other line of the picture, so it's squashed vertically; upstream drew only the backdrop there. Interlace mode 1 draws as normal resolution.

## Testing

The host simulator is in the Viper firmware repo, with this repo at `apps_public/`. There `make sim-test` builds the app into the simulator and runs its tests (listed in this repo's `tests.cmake`), and the all-apps and leak tests open it. In the firmware repo:

```bash
make sim-affected
./build-sim/tests/viper_sim_app_tests "[genesis]"
./build-sim/tests/viper_sim_app_boot_tests "[genesis]"
VIPER_SIM_GENESIS_SHOTS=/tmp/shots ./build-sim/tests/viper_sim_app_boot_tests "[genesis]"
```

To try a game in the simulator, put it in `.viper-sim/sdcard/roms/` and run `make sim-run` there. The test ROMs (`smoke.md`, `genesis/smoke_im2.md` and `genesis/smoke_md.h`) are generated by the firmware repo's `sim/tests/roms/make_test_roms.py`; change them there.
