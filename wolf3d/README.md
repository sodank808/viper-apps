# Wolfenstein 3D

Status: runs in the host simulator with the shareware episode; not yet tried on a device. Current as of 2026-11-22.

Wolfenstein 3D as an ELF app: [Wolf4SDL](https://github.com/KS-Presto/Wolf4SDL), the portable C port of [id Software's source](https://github.com/id-Software/wolf3d) (which is 16-bit DOS C and assembly), with Viper's platform in place of SDL. It plays the shareware episode, v1.4 (`*.WL1`).

## The game's data

id released the code, not the game's data. The shareware episode (Episode 1, "Escape from Wolfenstein", ten levels) is freely distributable unmodified, but it isn't the repo's to carry, so it's fetched:

```bash
wolf3d/tools/fetch_shareware.sh
```

downloads id's `1wolf14.zip` from the [gamers.org archive](https://www.gamers.org/pub/games/wolf3d/official/), checks its MD5, unpacks it (it's an ARJ archive inside the zip; needs 7-Zip, `brew install sevenzip`), and copies the eight `*.WL1` files into `wolf3d/assets/` (gitignored). `make` installs them with the app, beside its `app.elf`, where it looks for them: copy `out/sdcard/elf_apps/app.viper.wolf3d/` to `apps/` on the device's SD card. Without them, the app says which are missing and where they go.

The full game (`*.WL6`) and Spear of Destiny are other builds of the engine (`main/engine/version.h`) and aren't supported.

## Playing

| Button | Playing | In the menus |
| --- | --- | --- |
| D-pad | Move and turn | Choose |
| Up twice, held | Run | |
| A | Fire | Select; "yes" |
| B | Open doors, push walls, take elevators | Back; "no" |
| B twice | Next weapon | |
| X (held) | Run | |
| Y | Next weapon | |
| L / R | Strafe | |
| Start | Menu | Back |

Some boards have no X and Y, so both have a double press too (`kDoublePressMs`, 250 ms between the presses): Up, let go and pressed again runs until it's let go, and B twice is the next weapon. So a single B, playing, opens a door only once a second press can't follow, a quarter of a second late; in the menus B goes back at once.

The app takes B for itself (`viper_app_handle_back(1)`), so it closes from the game's own Quit, or by holding Select as any app does (the game saves its config either way). The config (`config.wl1`) and saved games are in the app's data folder (`viper_data_path()`). The game's own help ("Read This!") describes the keyboard.

It installs to the SD card (`SDCARD_APPS` in the `Makefile`): the app is 300 KB and its data 1.2 MB.

It needs firmware that exports `pthread_mutex_*` and `pthread_cond_*` (below); older firmware refuses it when it's installed, naming the function.

## Layout

- `main/engine/`: the engine, Wolf4SDL at dc8b250 (2024-05-20, its last commit on GitHub), the files the shareware build uses. Every change is marked `Viper:`, except the reads of `grsegs[]` that became `CA_GrChunk()` (below). Left out: the SDL platform folders, MAME's OPL emulator (not GPL; `USE_GPL` picks DOSBox's, `dosbox/`), and the optional features (`wl_plane.c`, `wl_atmos.c`, ...).
- `main/engine/wolf_sdl.h`, `wolf_sdl.c`: the SDL types and the few SDL calls the engine still makes, for 8-bit surfaces.
- `main/engine/wolf3d_platform.h`: what the engine asks of the app.
- `main/engine/wolf_names.h`: generated by `tools/gen_names.py` (below).
- `main/wolf3d_app.cpp`: the app (`viper_app_t`), the engine's thread and the turn between it and `loop()`, video, input, files and memory.
- `main/wolf3d_sound.cpp`: the ring the audio tap reads, and the OPL.

## How it runs

- **The engine's thread.** Wolfenstein's code waits where it pleases (a fade, a menu waiting for a key, the next tic), as DOS programs did. So it runs on a thread of its own, and everywhere it would wait (`VW_UpdateScreen()`, `SDL_Delay()`, waiting for input) it hands the turn to `loop()` and waits for the next frame, through a mutex and a condition variable (`pthread_mutex_*` and `pthread_cond_*`, which the firmware exports for it). Only one side runs at a time, so neither needs locks of its own. `loop()` waits up to 100 ms for the engine's frame; a longer one (loading a level) carries on into the next.
- **Time** is the frame's: `SDL_GetTicks()` is `loop()`'s `now_ms`, which moves only when the engine waits for a frame. The simulator's tests run on simulated time, and so does the engine.
- **Video.** The engine draws its original 320x200 8-bit screen; `loop()` copies it to an indexed frame (`viper_frame_set_indexed()`), which the display stretches to the screen, with the game's palette, which changes as the player is hurt or picks things up.
- **Input.** The buttons are keys: each press sends the keys the game reads, which depend on whether it's playing or in a menu (`wolf3d_set_playing()`, set by `PlayLoop()` and the control panel), and its release lets go of the same keys. The game's key bindings are set to match at each start. The double presses are timed by the frames' time; a key that's tapped (the next weapon, a door after B is let go) is held for one frame.
- **Sound.** `SD_Mix()` (in `id_sd.c`, where SDL_mixer's callback was) makes the OPL2's output, the AdLib sound effects and the music, with DOSBox's dbopl, and mixes up to eight channels of digitized sound over it, at 22050 Hz. It runs on the engine's thread each time the engine hands over the turn, filling a ring 70 ms ahead of the audio tap, which reads it at the device's rate. The digitized sounds are played as they are (8 bits, 7042 Hz), each read from the page file the first time it plays.
- **Leaving.** `Quit()` (the game's own, or an error) goes back to the top of the engine's thread with `longjmp()`. When the app closes mid-game, the engine quits from where it waits, as the game's Quit would (saving the config, shutting down).

## Memory

Wolf4SDL reads all of the page file (VSWAP: walls, sprites and digitized sounds, 660 KB) and all of the graphics (450 KB) at the start; its heap peaked at 1.4 MB. A device has about 1.2 MB of PSRAM free at the home screen (with 8 MB of PSRAM), less the app's own 370 KB once it's loaded, so here:

- **Pages** are read as the game asks for them (`id_pm.c`), into a cache that gives up the least recently used. A page is never given up in the frame it was asked for, since the renderer holds its walls' and sprites' pages until the frame is shown (`PM_NextFrame()`). The cache's size is what PSRAM has free less 512 KB, between 128 KB and 576 KB (all of the shareware's walls and sprites); the simulator's is 192 KB, so its tests page as a device would.
- **Graphics** are read as they're used (`CA_GrChunk()` in `id_ca.c`, from the file kept open), and the whole-screen pictures (the title screens, 64 KB each) are given up once drawn.

That brings the heap's peak to 360 KB in the simulator with its 192 KB cache. Every block goes through `wolf3d_malloc()`, which keeps a list, so closing the app frees all of it, wherever the engine was.

## Fixes to Wolf4SDL

- `CA_CacheMap()` left GAMEMAPS open, a file each level.
- `CA_LoadAllSounds()` read the sounds again at each level, freeing the AdLib sound playing; now it keeps them when the sound mode hasn't changed.
- `#pragma pack(1)` covered the whole engine: it's now only on the structs read whole from the data files (`maptype`, `mapfiletype`). The static tables it packed put pointers at odd addresses (which macOS's linker refuses) and slowed every access to them on the device.
- `itoa()`/`ltoa()` sized their output by what the buffer held before; they now take its size.

## The simulator

The simulator compiles every ELF app into one program (`sim/CMakeLists.txt`), which brings two things a device doesn't have:

- **Names.** The engine's globals (`screen`, `player`, `Quit`, `viewwidth`, ...) would meet other apps' and the firmware's. `wolf_names.h`, included first by `wl_def.h`, gives each the prefix `wolf_`. Run `tools/gen_names.py` after adding or removing a global in the engine. The app's own C++ doesn't include it (it would rename the app's names too), so it calls the engine's functions by their prefixed names (`wolf_SD_Mix()`, `wolf_Quit()`).
- **Globals keep their values** from one launch to the next, where a device loads the app afresh. Built with Clang, the simulator puts the engine's variables in sections of their own (`#pragma clang section` in `wl_def.h`), which the app copies when it first opens and puts back before it starts the engine again. GCC can't place a whole file's variables, so a simulator built with it runs the game once, and then says to restart it.

Expect UndefinedBehaviorSanitizer reports from the engine in the simulator's log (dbopl's tables made through null pointers and with signed overflow, a shift of a negative number in `wl_state.c`); they're upstream's, and harmless on the device.

## Testing

The simulator is part of the firmware repo, with this repo at `apps_public/`: its `make sim-test` builds the app in, and the all-apps and leak tests open it once it's installed (`make apps` there). Its own tests are in `tests/test_wolf3d_boot.cpp`, and install the app themselves: without the data it says what's missing and any button closes it; with the data (`tools/fetch_shareware.sh`, which the tests install from `assets/`, or a folder of `*.WL1` named by `VIPER_SIM_WOLF3D_DATA`) the game is played three times over: the title screens, the menu and Read This!, a new game, walking, firing, a door, the double presses and the level's music, then closing from the menu, checking that nothing grows from one launch to the next. Without the data that test is skipped.

```bash
./build-sim/tests/viper_sim_app_boot_tests "[wolf3d]"   # in the firmware repo
```

`VIPER_SIM_WOLF3D_SHOTS=<dir>` saves each screen. To play it in the simulator, fetch the data, then `make apps` and `make sim-run` in the firmware repo.

Not yet known, since it hasn't run on a device: the frame rate, how much the page cache reads from the SD card as the player turns, whether the engine thread's 32 KB stack is enough, and whether mixing the OPL keeps up.
